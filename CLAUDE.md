# Virallink (ex-« Veille virale ») — notes pour Claude

Application web par abonnement (Flask) qui repère les Reels et carrousels Instagram/TikTok viraux de comptes à copier, les analyse (vidéo, transcription, slides) et les adapte à la niche de l'utilisateur avec Claude. Le propriétaire est francophone : code, interface, messages et commits en **français**.

## Lancer et tester
- `python app.py --demo --port 8000` : application complète avec données fictives (aucune clé API consommée). Sans clés dans `.env`, le mode démo est automatique.
- `python veille.py --demo` : moteur en ligne de commande.
- Pas de suite de tests : vérifier chaque changement en mode démo (inscription → assistant → analyse → galerie), sur ordinateur et à 390 px de large.
- Dépendance système : ffmpeg (avec libass). La lecture des commentaires a été retirée (coût Apify, peu utile).

## Architecture
- `app.py` : serveur, API JSON, file de tâches (une à la fois), veille automatique du lundi.
- `abonnements.py` : utilisateurs SQLite (`data/app.db`), formules (`plans.yaml`), quotas, Stripe sans SDK.
- Formule gratuite (`gratuit` dans `plans.yaml`) : fin d'essai, résiliation ou impayé y basculent automatiquement (`abonnements.plan_effectif`). Ses options (`ia`, `montage_reel`, `suivi_publications`, `sequences_emails`, `filigrane`, `mention_boutique`, `commission_boutique`) se vérifient avec `reserve(u, option)` dans `app.py` ; une analyse y est un simple classement (`moteur.executer(classement_seul=True)`).
- `espace.py` : un dossier par client dans `data/espaces/<id>/` (config.yaml, historique, analyses, médias, suivi).
- `moteur.py` : orchestration d'une analyse (`executer`), adaptation unitaire, assistant (analyse du compte, hashtags).
- `collecte.py` (Apify ; Reels, carrousels, son utilisé), `video.py` (ffmpeg + Whisper), `suggestions.py` (comptes Instagram ou TikTok à copier proposés par Claude puis vérifiés par collecte, compte par compte ; TikTok : 12 candidats × 8 vidéos car sa collecte coûte ~30× plus cher), `banque.py` (images et vidéos libres de droits Pixabay ou Pexels, démo sans clé), `commentaires.py`, `ia.py` (tous les appels Claude, sorties forcées par outil), `selection.py`, `apprentissage.py`, `decouverte.py`, `rapports.py`.
- `studio.py` : studio de création (carrousels Pillow, Reels montés ffmpeg + libass avec hook et sous-titres Whisper, diaporamas, couvertures de Reel en 7 styles avec aperçu grille 3:4, package ZIP). Typographie : 81 polices en 7 styles (`STYLES_TYPO`, `_PLUS`), tailles du titre et du texte + casse par projet (`typo_reglages`, résolus par `_typo`/`typo_projet`) ; polices ajoutées figées en gras et nommées « VV … » pour libass. `studio_styles.py` : 108 styles de carrousel classés en 10 familles de couleurs (`FAMILLES`, `GABARITS` × `_PALETTES` → `MODELES` : fond texturé numpy/Pillow, couleurs, typo, numéro, surtitre, note manuscrite) choisis par `p["modele"]`, couleurs du titre et du texte par `p["couleurs_texte"]` (aussi hook et sous-titres des Reels), résolus dans `theme_de`. File de tâches séparée (`FILE_STUDIO`), quota `studio_par_mois`.
- `plan30.py` : plan de contenu de 30 jours (onglet Studio, `renduPlan30` dans `index.html`) : 8 carrousels en tunnel de vente (storytelling → éducatif → preuve sociale → vente, mardi et vendredi sur 4 semaines, `SEQUENCE`). Les publications de toutes les veilles sont regroupées par catégorie du tunnel d'après leur `type_contenu` (`TYPE_VERS_CAT`) et triées (adaptées, virales, carrousels, score) ; chaque case reprend la STRUCTURE de la meilleure publication de sa catégorie, jamais son texte ni ses images. Infos de vente données une seule fois par boutique (`plan30/brief.json`, `brief_<bid>.json` pour les boutiques suivantes ; l'offre se choisit parmi les produits de la boutique, `_produits_plan30`, un ou plusieurs (cases à cocher, `ids30`/`choisis30` : ids dans `produit_id` séparés par des virgules, liste `produits` « titre (prix) » ; plusieurs → lien vers la boutique et chaque carrousel de vente met en avant un seul produit, `_contexte_brief`) ; ensuite chaque nouveau plan s'ouvre directement sur le dernier écran : dates du mois) : offre, cible, problèmes, objections, témoignages réels seulement, histoire, ton) ; sujets des 8 cases écrits par `ia.ecrit_plan30`. Fabrication (`fabrique`) = projet du studio + `ecrit_textes` avec `p["consigne_plan"]` (passé à `IA.carrousel(tunnel=…)`) + banque d'images + `genere` ; 1 création au studio par carrousel. Quota `plans_30j_par_mois` dans `plans.yaml`. API `/api/plan30*`.
- `boutique.py` : boutique en lien dans la bio (page publique `/@pseudo`, thèmes et design, produits numériques, capture d'e-mails, kit média, statistiques). Produit « Vendre via un lien d'affiliation » (`externe`, affiliation ou plateforme de formation) : son bouton mène à `lien` via `/@pseudo/p/<pid>/ouvrir`, sans Stripe, et ne compte pas dans l'étape « activer les paiements ». Paiements via Stripe Connect sur le compte de chaque cliente (`BOUTIQUE_COMMISSION` en %, 0 par défaut) ; achats simulés en démo. Données dans `data/espaces/<id>/boutique/`, pseudos uniques dans la table `boutiques`. Mises en page (`design.mise_en_page` : colonne, bento, magazine ; `_css_mise_en_page`) avec espacement, largeur de page et taille du texte ; 126 thèmes en 7 ambiances (dont Bento et Éditorial, allures `tuiles*` et `edito`). Chaque bloc est enveloppé par `_bloc_enveloppe` : largeur sur une grille de 6 colonnes (`largeur` : plein, deux_tiers, demi, tiers), `hauteur` (bento) et `style` propre (fond, texte, forme, bouton, taille, align, police). Blocs : lien, titre, texte, vidéo, produit(s), capture, kit, image, galerie, témoignages, FAQ, compte à rebours, bannière, séparateur, musique (`lecteur_musique`). Polices : une feuille Google Fonts par famille. Un bloc « lien » peut porter `produit` : le bouton mène alors à la page de paiement (`/@pseudo/l/<bid>` → `/@pseudo/p/<pid>?src=bouton`) ; raccourci « Bouton de paiement » dans la liste des blocs. Création guidée pas à pas : toutes les questions d'abord, puis Virallink fabrique la boutique (`renduAssistantBoutique`, étapes `etapesBoutique`) : nom → adresse proposée à partir du nom, variante libre proposée si elle est prise (`?variante=1`) (crée la boutique en brouillon) → logo (ses couleurs : `palettes_photo`) → produits (`TYPES_NP` : e-book/fichier, produit sur un autre site, affiliation, séance, cadeau ; un écran par question, `A.np`, `NB_ECRANS_NP` ; fichier envoyé dans Virallink, nom tiré du fichier ; pour un lien (ou plusieurs, un par ligne : `N.lots`, une fiche à vérifier par produit, ajoutés d'un coup), `POST /api/boutique/importe_lien` → `import_lien.lit_page` lit la page (Open Graph, JSON-LD) et récupère nom, phrase, image et prix, sans IA, protégé contre les adresses internes ; enregistrés aussitôt par `ajouteProduitAssist`) → paiements si produit payant hors lien externe (« As-tu un compte Stripe ? » : relier ou créer via `/api/boutique/stripe`, état gardé dans `sessionStorage.vv_assist` pendant l'aller-retour, ou plus tard). Parcours en cours gardé sur le serveur (`/api/boutique/parcours`, `parcours.json` dans le dossier de la boutique, `gardeAssist`/`reprendAssist`/`oublieAssist`, copie de secours dans le navigateur) : reprise sur un autre appareil, via « Continuer ma boutique » ou « Ma boutique » → « Qui sont tes clientes ? » → « Tu les aides à quoi ? » → présentation : 3 propositions écrites par Virall.ai (`POST /api/boutique/bio` → `boutique_ia.bios` → `ia.ecrit_bios`, modèle léger, file `FILE_STUDIO`, option `ia` ; sans droit ou en cas d'échec, phrases toutes faites `biosModeles`), « Autres propositions », retouchable → réseaux → 3 propositions de design avec la vraie page (`propositionsDesign` : maquettes soignées `MAQUETTES` — Essentiel, Boutique, Moderne, Élégant : en-tête minimal, logo à sa taille, cartes produits propres, sans décor — habillées des couleurs du logo puis de `PALETTES_CHOISIES` ; `designProposition` → `A.design`, utilisé pour l'aperçu et la mise en ligne ; navigation « ← Précédentes » / « Autres → » et rappel de la boutique choisie ; logo enregistré dans la page dès l'envoi) → mise en ligne. Avant la création, `/api/boutique/apercu` part de `page_initiale` et les images passent par `/api/boutique/i/<nom>` ; produits d'exemple `PRODUITS_EXEMPLE` dans l'aperçu seulement. Dans l'éditeur, carte « Prochaine étape » (`majSuite`, `etapesBoutiqueRestantes` : produit → contenu à livrer → paiements si produit payant hors affiliation → mise en ligne → « Boutique prête », refermable), recalculée à chaque enregistrement.
- Plusieurs boutiques par compte : identifiant de boutique « bid » = id de l'utilisatrice pour la première (dossier `boutique/`), `"<uid>-<n>"` pour les suivantes (dossier `boutiques/<n>/`), stocké dans la colonne uid de la table `boutiques` (`bq.proprio`, `bq.bid_propre`, `bq.boutiques_de`, `nouvelle_boutique`, `supprime_boutique`). Boutique ouverte dans l'éditeur : `session["bq"]` via `bq_active()` (toutes les routes `/api/boutique*` l'utilisent) ; tout ce qui concerne la propriétaire (droits, profil, notifications, usage) passe par `bq.proprio(bid)`. Nombre par formule : `boutiques` dans `plans.yaml` (`max_boutiques`). API `/api/boutiques` (liste), `/ouvrir`, `/nouvelle` (402 au-delà), `DELETE /api/boutiques/<bid>` (toute boutique, la première comprise : page, produits, inscrites et ventes effacés, adresse libérée ; la cliente repart de la création pas à pas). Écran « Mes boutiques » : `mesBoutiques()` ; une nouvelle boutique démarre par la création pas à pas.
- Parcours « Ajouter une offre » (`nouvelleOffre`, `assistantOffre`, état `BQ.offre`, dans l'onglet Produits, classe `en-offre` qui masque l'en-tête de l'éditeur) : une offre = le produit + sa présentation, mis en ligne d'un seul geste. Écrans : comment tu la vends (`MODES_OFFRE` : fichier, séance, affiliation, cadeau gratuit) → nom, prix, image, fichier ou lien → présentation (page de vente conseillée, quiz, fiche simple ; page de vente et quiz réservés aux formules avec `tunnels`) → aperçu et « Mettre en vente » (`metEnVente` : produit + tunnel + bloc produits + boutique en ligne, puis envoi du fichier) → « C'est en vente » (relier Stripe si besoin). Page de vente écrite par Claude (`POST /api/boutique/page_vente` → `boutique_ia.page_vente` → `ia.ecrit_page_vente`, file `FILE_STUDIO`, quotas `ia` + `tunnels`) posée sur le modèle `vente_formation`/`vente_accompagnement` ; sans droit, le modèle pré-rédigé reste. Ajouter une page de vente à un produit existant : `pageVenteProduit` (bouton de la fiche produit). L'onglet Tunnels n'existe plus : les tunnels s'ouvrent depuis leur produit (`editeTunnel`, « ← Mes produits ») ; une page de vente est en ligne dès que son produit est visible (`bq.tunnel_en_ligne`). Liste des produits avec état « ✓ En vente » / « ⚠️ Il manque… ». La création pas à pas de la boutique crée elle-même les produits ; « Ajouter une offre » sert ensuite (page de vente, quiz). Accueil : Crée ta page → Ajoute ta première offre → Partage ton lien (`prets` dans `boutique_etat`).
- `tunnels.py` : tunnels de vente de la boutique, réservés aux formules payantes (option `tunnels`, coupée dans `gratuit`). Deux types : quiz-audit noté (questions notées 0-4 par critère → note /100 et /20 par critère, point bloquant, actions prioritaires, e-mail facultatif, niveaux, offre) et page de vente (promesse, problème, bénéfices, contenu, témoignages réels seulement, à propos, FAQ, offre). Modèles pré-remplis `MODELES` (sans IA), nettoyés par `tunnels.propre`, rangés dans `page["tunnels"]` (PUT `/api/boutique`). Pages publiques `/@pseudo/t/<id>`, e-mail `/@pseudo/t/<id>/email` (inscrits), bouton `/@pseudo/t/<id>/offre` → produit (`?src=tunnel-<id>`). Statistiques `bq.stats_tunnels`. Création guidée pas à pas (`assistantTunnel`, étapes `etapesTunnel` : type → modèle → promesse avec exemples → critères/questions/résultat/e-mail ou problème/bénéfices/confiance/FAQ → offre avec création rapide de produit → partage et mise en ligne ; encadré « Pourquoi ? » à chaque étape). Styles propres au tunnel (`tunnels.STYLES` : 15 styles Sombre/Clair/Coloré, couleurs + polices + variantes `v-halo`, `v-cadre`, `v-impact`, `v-doux` ; `t["style"]`, vide = thème de la boutique), choisis à l'étape « Ton design » ou dans l'éditeur avec vignettes d'aperçu réelles (`choixStyleTunnel`/`lieStyleTunnel`). Un produit vendu par un tunnel en ligne (`bq.tunnel_du_produit`, `page["_tunnels_ok"]` posé par `_vitrine`) : sa carte mène au tunnel, et `/@pseudo/p/<pid>` sans paramètre y redirige (le bouton d'offre du tunnel passe `?src=tunnel-…`, donc pas de boucle). Sinon, un tunnel s'annonce par un bloc « lien » portant `tunnel` (ajouté en tête à la mise en ligne par `metTunnelSurPage` si la carte du produit n'est pas déjà sur la page, ou depuis la liste des tunnels ; masqué tant que le tunnel n'est pas en ligne ; `/@pseudo/l/<bid>` → `/@pseudo/t/<id>`). Création rapide de produit dans le tunnel avec lien d'affiliation facultatif ; alerte si le produit de l'offre n'a rien à livrer. Raccourcis : bouton « Créer un tunnel » dans la fiche produit (`#pr-tunnel`, `BQ.tnAssist.produit` pré-choisit l'offre) et dans la carte « Boutique prête ». Éditeur détaillé : `editeTunnel` (champs `outilsTunnel`, liés par `data-tp` via `lieChampsTunnel`), aperçu vue `t:<id>`.
- `messages_auto.py` : messages privés automatiques sur Instagram (façon ManyChat) : quand quelqu'un commente un mot-clé, Instagram lui envoie en privé un lien (boutique, produit, page de vente, `?src=dm`) avec bouton, plus une réponse publique tirée au hasard. API Instagram avec connexion unifiée (« Unified login », imposée par Meta aux nouvelles applications depuis octobre 2026 : Facebook Login for Business + `config_id`, graph.facebook.com, `VERSION`) : la cliente se connecte avec Instagram ou Facebook, choisit son portefeuille et son compte (`/instagram/connexion` → `/instagram/retour`, `me/assigned_instagram_accounts`, `<ig_id>/subscribed_apps`), table `instagram` (jeton d'utilisateur système du portefeuille, sans expiration avec la configuration « Jamais »). Webhook `/api/instagram/webhook` (signature X-Hub-Signature-256 avec `INSTAGRAM_APP_SECRET`, jeton de vérification `jeton_webhook(app.secret_key)` affiché à l'admin), traité en fil séparé (`traite_webhook`) ; une réponse par commentaire (`repondus`), `MAX_PAR_HEURE`, journal 60 jours. Désautorisation et suppression des données : `/instagram/desautorisation`, `/instagram/suppression`. Règles dans `data/espaces/<uid>/messages_auto.json`. Option `messages_auto` (coupée dans `gratuit`). Écran « Messages auto » (sous-onglet de Boutique, `renduMessages`, assistant 6 étapes `etapesMessage`) ; mode démo simulé ; sans clés Meta en production : « Bientôt disponible ». Variables Railway : `INSTAGRAM_APP_ID` et `INSTAGRAM_APP_SECRET` (application Meta « Virallink » du portefeuille Kcoaching), `INSTAGRAM_CONFIG_ID` (configuration à 3 autorisations : instagram_basic, instagram_manage_messages, instagram_manage_comments), `INSTAGRAM_WEBHOOK_TOKEN`. Pas de coût d'API (Meta est gratuit), mais l'app Meta doit passer la vérification (App Review) avant d'ouvrir aux clientes : d'ici là, seuls les admins voient la vraie connexion (`_ig_ouvert`), `INSTAGRAM_OUVERT=1` l'ouvre à toutes.
- `boutique_ventes.py` (prix en promo et compte à rebours, codes promo, avis vérifiés, packs, offre complémentaire, rendez-vous, sources des visites, QR code, séquence d'e-mails envoyée par `planificateur_emails`), `boutique_ia.py` (idées de produits, guide PDF, séquence écrite par Claude : file `FILE_STUDIO` et quotas ; le guide reste en brouillon `guides/<pid>.json` avec ses pages en JPEG (pypdfium2, sous verrou `_PDFIUM`) jusqu'à validation : relecture `apercuGuide()` dans `index.html`, corrections sans IA `met_en_page`, `valide_brouillon` l'attache au produit) et `guide_pdf.py` (reportlab, A5).
- `notifications.py` : notifications push (Web Push, clés VAPID dans `data/vapid.pem`, chiffrement aes128gcm sans dépendance) ; application installable (`/manifest.webmanifest`, `static/sw.js`, `static/icones/`). Parrainage dans `abonnements.py` (code, mois offerts), récapitulatif du lundi (`envoie_syntheses`), boutiques en exemple sur l'accueil (`/api/vitrines`).
- `emails.py` (Resend, sans SDK), `legal.py` + `societe.yaml` (CGV, confidentialité, mentions légales), `static/admin.html` (tableau de bord, réservé à `ADMIN_EMAILS`).
- Modèle : la boutique est gratuite et sans limite de durée (aimant à prospects, 1re étape de l'accueil : créer la page → ajouter un produit → activer les paiements → mettre en ligne, `_avancement_boutique` dans `/api/etat`). Tout nouveau compte, même venu de la boutique gratuite, a 7 jours d'essai de toutes les fonctions (`abonnements.cree`) ; ensuite, sans abonnement, formule gratuite : Reels, planning et Studio grisés avec un cadenas (`VUES_PAYANTES`, `majVerrous`, `va` renvoie vers Abonnement), étapes 2 à 5 de l'accueil verrouillées sous une carte « Débloquer ».
- Boutique gratuite (aimant à prospects) : `/boutique-gratuite` (`static/boutique-gratuite.html`, lien de la pastille « Créé avec Virallink ») → `/connexion?offre=boutique` → compte en formule gratuite avec `origine=boutique`, essai de la veille gardé en réserve (`essai_utilise=0`, `abonnements.essai_dispo` / `demarre_essai`, `POST /api/essai`). Propositions discrètes : `carteEssai` (refermables, 10 jours) et `proposeEssai()` dans `index.html` (une option réservée ouvre l'essai au lieu de la page Abonnement) ; e-mails J+2, J+5, J+10 (`envoie_relances_boutique`, `emails.conseil_boutique`).
- Passage à une formule payante : `#bandeau-offre` (essai en cours avec compte à rebours, urgent à J-2 ; essai terminé « veille en pause »), carte « publications écrites pendant ton essai » sur l'accueil, badge « Le plus choisi » (`abonnements.formule_conseillee`, envoyée dans `/api/etat` → `offre`), e-mails J-2 et J0 (`envoie_relances_essai`, `emails.fin_essai`, lien `/app?formules=1`). L'administrateur ne voit rien de tout ça, sauf en aperçu : `/app?apercu=essai&jours=1` ou `/app?apercu=fini`.
- `static/accueil.html` (page publique sur `/` quand on n'est pas connecté), `static/index.html` (application sur `/` ou `/app` : galerie, planning, studio, assistant, paramètres, abonnement) et `static/connexion.html` (inscription, connexion, mot de passe oublié) : HTML/CSS/JS sans framework.
- `ressources.py` : adaptation à la taille du serveur (limite mémoire cgroup) : vidéos d'une veille traitées une par une sur une petite machine, modèle Whisper libéré après usage (`libere_memoire`), ffmpeg lancé avec `preexec_fn=sacrifiable` (tué en premier en cas de manque de mémoire). Vidéo importée dans le Studio ramenée en 1080p H.264 SDR par une tâche de fond (`studio.optimise_video`).
- `nettoyage.py` : nettoyage automatique du disque une fois par jour (appelé par `planificateur`) : dossiers temporaires `veille*_*` de plus d'un jour, `data/cache` de plus de 3 jours, `rapports/brut_*.json` de plus de 14 jours, images de `media/` de plus de 30 jours citées par aucun fichier JSON/HTML/YAML de l'espace. Jamais : boutiques, studio, analyses, rapports Excel/HTML, réglages. Bilan dans `data/nettoyage.json`, affiché dans l'admin.
- `static/fonts/` : Poppins (OFL), utilisée pour les textes incrustés.
- `config.exemple.yaml` : modèle d'un nouvel espace client. `config.yaml` : usage local (CLI).

## Règles
- UX (`static/index.html`) : principe « un écran = une action » : une question ou un bouton principal par écran, pas d'encadré d'explication (`guide()` ne renvoie plus rien), détails rangés derrière « Filtres » ou « Voir plus ». L'accueil montre les 5 étapes numérotées (boutique → veille → plan du mois → créer → publier), l'étape en cours ouverte avec un seul bouton. Sur téléphone, 5 onglets en bas (« Moi » regroupe résultats, profil, comptes, abonnement via `groupes()`). Suppressions avec `toastAnnuler(...)` plutôt que `confirm()`, chargements avec `squelette()`, boutique en mode simple par défaut (classe `avance` pour les options cachées, `BQ.avance`).
- Ne jamais committer `.env`, `data/`, `rapports/`.
- Coûts : plafond mensuel `budget_usd` par formule (`plans.yaml`, vérifié dans `abonnements.peut` sur `usage.cout_usd`) ; coût IA calculé selon le modèle (`ia._compte`, `PRIX_MODELES`), classements sur le modèle léger (`MODELE_LEGER`). Pas de repli vers le collecteur Instagram standard (54× plus cher) sauf `APIFY_SECOURS=1` ; découverte par hashtags coupée sauf `DECOUVERTE_HASHTAGS=1` (3 hashtags, 20 posts max). Veille : seules les `adaptations_auto` (7) meilleures publications sont adaptées d'office (`moteur.a_adapter_d_office`), les autres du planning le sont à la demande (« à adapter », bouton `data-adapter`). Veille automatique du lundi en traitement différé à moitié prix (`ia.adapte_tous_differe`, Batch API ; file libérée pendant l'attente via `FIL.verrou`, lot mémorisé dans `lot_<aid>.json` ; `LOTS_DIFFERES=0` pour couper).
- Toute nouvelle consommation d'API doit respecter les quotas (`abonnements.peut`) et passer par la file de tâches. Elle exige aussi une adresse e-mail confirmée : `refus` (analyses/adaptations) et `reserve` (`ia`, `montage_reel`, `sequences_emails`) lèvent `AdresseNonConfirmee` → 403 `verification` (fenêtre « Confirme ton adresse » côté client). Lien signé `abonnements.jeton_confirmation` → `/confirmer` ; exigé seulement si les e-mails sont actifs ; adresses jetables refusées à l'inscription (`DOMAINES_JETABLES`).
- Les textes générés ne doivent pas « sonner IA » ; respecter les interdits de la niche de chaque client.
